## 1. プロダクト

nuriは、SNSで見つけたメイクの手順を「レシピ」として選び、インカメラに映る自分の顔へ塗る範囲と色を重ねて、1手順ずつ再現できるモバイルアプリ。

- **利用者:** SNSのメイク動画を真似したいが、自分の顔だと位置や量が分からない人。メイク初心者から、新しいメイクを試したい人まで。
- **課題:** お手本と自分の顔は形が違うため、「どこに・どれくらい」塗るか分からない。メイク中は両手がふさがり、動画を止めたり戻したりしにくい。色や成分が自分に合うかを買う前に確かめにくい。
- **価値:** レシピをSNSの投稿からも作れる。自分の顔に塗る範囲と色が重なり、手順を進めながら塗れる。完成形を確かめられる。
- **言葉:** 要件資料のキャッチコピーは「自分の顔で、手順どおりに。」、実装planのログイン画面は「あの子のメイクをわたしの顔で」。どちらを表に出すかは未決。

### ハッカソンの制約（確定）

- コードフリーズと提出は **2026年11月10日（火）19:00**。以後は提出リポジトリが読み取り専用になる。決勝進出チームはDemo Day（11月27日）まで追加開発できる。
- アプリの実行に Google Cloud の実行基盤（Cloud Runなど）を使う。APIはCloud Runで動かす（スターターの構成）。デプロイURLはRegional Day（11月14日）まで動かし続ける。適用の時期・規模・費用は[設定手順](setup.md#適用の時期規模費用)に記録した。
- 主要な技術スタックはGoogle技術にする。他社のLLM APIは使えるが「Google技術の活用」で評価されない。顔追跡のMediaPipeはGoogle技術。
- 審査は8項目×0〜3点。うち3項目が完成度（一連の流れが動くか、UI・UX、安全性・拡張性・保守性）。
- 提出物はGitHubリポジトリ、プロダクト説明ドキュメント、デモ動画、著作物利用シート（素材・ライブラリ・データの出典とLicense）。APIキーや秘密情報をコミットしない。

## 3. 機能要件

各機能の画面番号は実装planのものを使う。受け入れ条件は、その機能を完成とみなす最低限の条件。

### F1 レシピを探す（P0：①⑤、P1：②③）

- **①ホーム（全体）:** 上部にロゴ「nuri」と検索バー（「メイクを検索」、右端に「動画URL」ボタン）。その下に「全体（顔まるごと）」「部位（パーツ別）」の切り替え。レシピカードを2列で並べ、各カードに写真、題名、投稿者、いいね数、保存ボタンを置く。SNS取り込みの入口は検索バーの右端に置く（実装planの「A案」）。
- **②ホーム（部位）:** 8部位（ベース、眉、アイメイク、まつげ、チーク、シェーディング、ハイライト、リップ）のカードとレシピ数。
- **③部位別一覧（眉）:** 絞り込み（すべて、丸顔におすすめ、初心者OK、ナチュラルなど）、眉の形の写真カード6種（平行眉、微アーチ眉、アーチ眉、ストレート眉、上がり眉、下がり眉）。選んだ形で「メイクをはじめる」。
- **⑤レシピ詳細:** 完成形の顔写真の上に、手順番号のピン（1眉、2シャドウ、3ライン、4シェード、5チーク、6リップ）を置く（Plan A）。実装では写真をそのレシピの画像にし，ピンは置かない（#193．画像の顔に置くと見づらかった）．題名、タグ（例：#丸顔向け、#15分、6ステップ）、投稿者と取り込み元（例：「Instagramから取り込み・保存1.2k」）、フォロー、手順のアイコン列、使うメイク品の一覧（件数つき）、お気に入り、共有、保存、「メイクをはじめる」。
- **受け入れ条件:** ①でレシピを選ぶと⑤が開き、「メイクをはじめる」で⑦の1手順目が開く。データが0件・取得失敗・読み込み中の表示がある。

### F1-2 SNSから取り込む（P1：④-1〜④-E）

- **④-1 URLを入力:** シート「SNSの動画をレシピにする」。URL入力欄、クリップボードにリンクがあれば「コピーしたリンクがあります・使う」、対応サービスの説明（Instagram・YouTube・TikTok）、最近取り込んだ投稿、「読み取る」。
- **④-2 読み取り中:** 投稿のサムネイル・題名・投稿者、進捗バー、段階（投稿を開く、メイクの手順を探す、使っているコスメを探す）、「キャンセル」。
- **④-3 読み取り完了:** 見つけた手順の数と部位のアイコン、検出したコスメの数と「確認する」、「レシピとして保存」。
- **④-4 読み取った手順を確認:** 元の投稿へのリンク、手順ごとの部位・説明・動画の区間（例：0:48）、各手順の編集メニュー。
- **④-5 保存完了:** 「レシピに保存しました」、手順数・コスメ数・元の投稿へのリンク付き、「自分の顔で試す」「レシピを見る」。
- **④-E 読み取れなかった場合:** 理由の例（投稿が非公開、メイクの手順が映っていない動画、対応していないサービスのURL）と「別のURLを試す」。
- **権利（確定）:** 取り込んだレシピには投稿者名と元の投稿へのリンクを必ず表示する。
- **取得方針:** 任意の投稿URLからの自動取得は採用しない。現状の④は「準備中」とだけ出すシートで、通信も保存もしない（#262）。利用者が元投稿を見ながら自分の言葉で手順とコスメを入力し、元URLを添える経路を次の候補とする。投稿の映像・字幕・説明文・画像の複製やGeminiへの送信は、サービスの条件と権利者の許可を個別に確認するまで行わない。調査と後続作業は[9章](#9-sns投稿の取得と権利の判断)に記録する。

### F2・F3 自分の顔で塗る（P0：⑦-1〜⑦-5）

Figmaの「参考：AR表現の比較（D採用）」（Screensページの「参考・検討」に移動）で採用されたD案（UVテクスチャで仕上がりの色を重ねる）で描く。処理は「[11. AR表示の方式](#11-ar表示の方式)」に従う。

- **上部:** 閉じる、題名と進捗（Plan Aの例：「狐メイク 1/6」、実装planは「1/5」）、重ね表示の切り替え（目のアイコン）、手順数ぶんの進捗バー。
- **手順カード:** 番号、見出し、補足、音声の状態（「音声ON」）。
- **顔の上:** 塗る範囲を仕上がりの色で乗算して重ねる。Plan Aでは要点にピンとラベル（例：眉頭・眉山・眉尻）、動かす向きの矢印、位置を決める補助線（例：小鼻→目尻→眉尻）を置き、細かい塗り方を円形の拡大表示（GIF）で示していた。実装planは実装に合わせ、部位ごとにピン1つと部位名のラベルを置く。
- **下のパネル:** 使う商品（色見本、名前、おすすめ色のカラーコード、デモ再生）、部位の手順列（済み・今・未着手）、「戻る」「次へ」、マイク。
- **手順の例（狐メイク、Plan Aの文言）:**

| 手順       | 見出し                     | 補足                               | おすすめ色                    |
| ---------- | -------------------------- | ---------------------------------- | ----------------------------- |
| 1 眉       | 眉尻を濃く、眉頭は淡く     | スクリューブラシで眉頭の毛を立てる | `#79513A`                     |
| 2 シャドウ | 目尻側から横長にぼかす     | 中間・締め色は目頭側へ薄く         | `#E5B58A` `#C56D42` `#713E2C` |
| 3 ライン   | 黒目の外側から徐々に太く   | 目尻は斜め上に跳ね上げ三角を埋める | `#38251D`                     |
| 4 シェード | 骨の凹みに沿って滑らせる   | 外側から内側へ境目を馴染ませる     | `#A17B60`                     |
| 5 チーク   | こめかみへ斜め上に滑らせる | 頬骨の高い位置から丸く広げない     | `#B8754F`                     |
| 6 リップ   | Plan Aに画面なし           | —                                  | —                             |

- 手順には見出し・補足・使う物・おすすめ色を必ず持たせる。Plan Aでアイコンだけだったリップは、狐メイクの見本の手順に入れない（#30で決定）。そのため⑤⑦⑪の狐メイクは5手順で、Plan Aの「6ステップ」と1つ違う。

- **受け入れ条件:** インカメラの顔に、今の手順の範囲が追従して重なる。「次へ」「戻る」と手順列で移動できる。顔が見つからない・カメラが許可されない・暗い場合に案内が出る。最後の手順の「次へ」で⑩へ進む。
- 要件資料の⑧ブラシの注釈は、Plan Aでは⑦の拡大表示に統合されていた。⑨塗れているかの判定は実装planに画面がない。

### F4 完成（P0：⑩、P2：⑪）

- **⑩完成:** 自分の顔（カメラの映像．⑦の塗る範囲の案内は重ねない，#190）、「Finish!」、「（レシピ名）のできあがり」、「次のメイクを試す」、保存（ダウンロード）。
- **⑪完成プレビュー:** 実装planでは非表示だが、全画面を再現する #13 で見た目を作る。Before・Afterの境目を指や読み上げ操作で動かせる。手順ごとのオン・オフは準備中として無効にする。
- 「お手本との近さ（%）」は算出方法が決まるまで表示しない。

### F5 塗れているかの判定（P2）

カメラ映像の範囲内の色を塗る前と比べ、左右差や薄い箇所を伝える。照明の補正が必要。実装planに画面がないため、作る場合は画面から設計する。

### F6 音声・顔のジェスチャーで操作（P2）

⑦の「音声ON」とマイクボタンは実装planにある。端末内で決まった言葉（「次」「戻って」「もう一回」）だけを聞き取る。P0ではマイクを表示だけにせず、機能が入るまでは無効状態で見せる（スターター規約：有効な操作は必ず働く）。

### F7 写真からメイク提案（P2：⑬⑭）

- **⑬:** 「似合うメイクを見つける」、カメラの顔に輪郭と比率の補助線、「顔の形を見ています…」、写真から・カメラで診断・前回の診断。
- **⑭:** 顔タイプ（例：丸顔×イエベ、たれ目、中顔面短め）、部位ごとの診断（今の形と似合う形、おすすめの色、その部位のメイクへ）。
- 顔の形・パーツの比率はFace Landmarkerの特徴点から計算できる見込み（案）。肌のトーン判定は照明に左右されるため未決。

#### 顔タイプと眉の診断（#47で決定，2026年11月7日〜8日）

最初は眉だけを対象にする．ほかの部位と肌のトーンは未決のまま残す．特徴点の計算は端末内で行い，写真はサーバーへ送らない．

**顔タイプと似合う眉:** 顔タイプは次の5種とする．各タイプの分け方は下記の「顔タイプの測り方（決定）」のとおり．

| 顔タイプ | 似合う眉   | 理由                                               | 出どころ                                   |
| -------- | ---------- | -------------------------------------------------- | ------------------------------------------ |
| 丸顔     | アーチ眉   | —                                                  | チームがInstagram・webサイトで調べた説     |
| 面長     | 平行眉     | —                                                  | チームがInstagram・webサイトで調べた説     |
| ベース型 | アーチ眉   | なだらかな曲線で，エラの角ばった印象をやわらげる   | AIによる仮の設定．チームで確認してから使う |
| 逆三角形 | 平行眉     | 横のラインで，広い額と細いあごのバランスをとる     | AIによる仮の設定．チームで確認してから使う |
| 卵型     | 微アーチ眉 | 標準的なバランスとされるため，自然な形を基本にする | AIによる仮の設定．チームで確認してから使う |

**顔タイプの定義:** チームがInstagram（lips_pon_の投稿）で調べた定義を使う．顔を4本の線で測る．赤は髪の生え際からあご先までの縦の長さ，黄は額の幅，青は小鼻の下の高さでの顔の幅，橙は口の高さでの顔の幅である．

| 顔タイプ           | 定義                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------- |
| 卵型               | 赤：青が4：3くらい．黄・青・橙が1：1：1に近く，青が少しだけ長い．顔のラインがやわらかい楕円型     |
| 丸顔               | 赤：青が4：3より円に近い．黄・青・橙が1：1：1に近く，青が少しだけ長い．顔のラインがやわらかい円型 |
| 面長               | 赤：青が4：3より細長い．黄・青・橙に比べて赤がかなり長い．頬に丸みがなく直線的                    |
| ベース型（四角顔） | 橙より下のエラの部分の横幅が長い．黄・青・橙が1：1：1に近く，特に青と橙がかなり近い．エラが直線的 |
| 逆三角形           | 赤：青が4：3より細長い．黄が一番長く，橙が一番短い．あごが尖り，頬骨が目立たない                  |

**顔タイプの測り方（決定）:**

1. Face Landmarkerの輪郭の点（36点）を，頭の傾きを除いた座標にする．
2. 次の長さをとる．
   - 赤：額の上部の点（10番）からあご先（152番）まで．Face Landmarkerには髪の生え際の点がないため，10番で代える．
   - 黄：眉と10番の中間の高さでの輪郭の幅．
   - 青：小鼻の下（2番）の高さでの輪郭の幅．
   - 橙：口（上下の唇と口角の平均）の高さでの輪郭の幅．
   - 下あご：口とあご先の中間の高さでの輪郭の幅（エラの張り）．
3. 青を1とした比（赤÷青，黄÷青，橙÷青，下あご÷青）で次の順に判定し，最初に当てはまったタイプにする．

| 順  | 顔タイプ | 条件                                                                                      |
| --- | -------- | ----------------------------------------------------------------------------------------- |
| 1   | 逆三角形 | 赤÷青 1.279以上（中央値）．黄÷青 1.0以上（黄が青より長い）．下あご÷青 0.649未満（中央値） |
| 2   | ベース型 | 橙÷青 0.915以上（上位25%）．下あご÷青 0.680以上（上位25%）                                |
| 3   | 面長     | 赤÷青 1.368以上（上位20%）                                                                |
| 4   | 丸顔     | 赤÷青 1.207未満（下位20%）                                                                |
| 5   | 卵型     | 上のどれにも当てはまらない                                                                |

境目は，Instagramの「4：3」ではなく，SCUT-FBP5500（下記）の分布の割合から決めた．人が付けた生え際で測っても赤÷青の中央値は1.49で，4：3（1.33）より小さい人は8%しかいなかったためである．割合（20%，25%，中央値）は仮に決めた．

**顔タイプの試算の結果（2026年11月8日）:** SCUT-FBP5500のアジア人女性2000人で，人が付けた輪郭の点（髪の生え際を含む22点）とFace Landmarkerの輪郭を比べた．

| 比        | 相関（人の点とFace Landmarker） | 人ごとの違い÷測り方のずれ |
| --------- | ------------------------------- | ------------------------- |
| 赤÷青     | 0.84                            | 4.6                       |
| 黄÷青     | 0.80                            | 3.6                       |
| 橙÷青     | 0.90                            | 5.7                       |
| 下あご÷青 | 0.87                            | 4.9                       |

人ごとの違いは10%〜90%の幅，測り方のずれは差の標準偏差である．眉と違い，輪郭は人ごとの違いを測れる．判定の内訳は卵型932人，逆三角形418人，ベース型317人，丸顔232人，面長101人．Face Landmarkerの輪郭と人の輪郭で同じタイプになった率は64%（偶然に一致する率は29%）．ただし，正解の顔タイプのラベルがないため，正しいタイプに分けられているかは確かめていない．

チームの写真（1人，4枚，インカメラ）では面長が3枚，逆三角形が1枚で，本人の印象（面長か逆三角形）と合った．ただし，橙÷青が0.81〜0.84で，SCUT-FBP5500の下位10%（0.864）より小さかった．顔の近くから撮ると写り方がゆがむためと考えられる（未確認）．

**顔タイプの決定:** 上記の定義，測り方，境目で顔タイプを5種に分け，⑭に出す．似合う眉は上の表のとおりとする．端末のカメラ（インカメラで撮る距離を含む）で比率を確かめ，境目と撮影の案内（顔から離して撮るなど）を見直すことは，写真から診断を実装するときに行う．

**眉の形の基準:** チームがInstagram・webサイトで調べた描き方の基準を使う．基準点は顔の特徴点で位置をとれる部位（小鼻，目頭，黒目の外側，目尻，口角）で表す．

| ------------ | ------------------------ | ------------------------------------------ | ---------------------------------------------------- |
| 平行眉       | 小鼻の延長線上           | 目尻の延長線上．眉頭と水平                 | 小鼻と目尻を結んだ延長線上．眉頭の下ラインと水平     |
| 微アーチ眉   | 小鼻の延長線上           | 黒目の外側と目尻の間．眉頭よりわずかに高い | 小鼻と目尻を結んだ延長線上．眉頭の下ラインと同じ高さ |
| アーチ眉     | 小鼻の延長線上．やや下め | 黒目の外側の延長線上．しっかり高い         | 小鼻と目尻を結んだ延長線上．眉頭より少し低い         |
| ストレート眉 | 目頭の真上               | 目尻の延長線上．眉頭とほぼ同じ高さ         | 小鼻と目尻を結んだ延長線上．短い直線で終える         |

**診断での眉の分類（決定）:** 平行眉とストレート眉は高さの関係がほぼ同じで，違いは眉頭の位置と輪郭の仕上げ（特徴点では測れない）だけである．そのため診断では1つにまとめ，5種に分類する．分類には，眉頭を基準にした眉山と眉尻の高さの差を使う．長さは目の横幅で割った値で表す．多くの人は眉山も眉尻も眉頭より高いため，境目は「0からの差」ではなく，人が付けた点の分布（下記の試算）から決めた．

| 診断での眉                   | 眉山の高さ（眉頭との差）   | 眉尻の高さ（眉頭との差）              |
| ---------------------------- | -------------------------- | ------------------------------------- |
| 平行眉（ストレート眉を含む） | 低め（0.161未満）          | ほぼ0〜少し高い（−0.03以上0.126未満） |
| 微アーチ眉                   | 中（0.161以上0.200未満）   | 少し高い（0.03以上0.126未満）         |
| アーチ眉                     | 高め（0.200以上）          | ほぼ0（−0.03以上0.03未満）            |
| 上がり眉                     | 高め（0.200以上）          | はっきり高い（0.126以上）             |
| 下がり眉                     | 問わない                   | 低い（−0.03未満）                     |
| 判定しない                   | 上のどれにも当てはまらない |                                       |

眉山の境目は人の点の分布を3等分する値，眉尻の「はっきり高い」は上位1/4の値である．「ほぼ0」と「低い」の境目（±0.03）は仮に決めた．

**眉の測り方（決定）:** Face Landmarkerの眉の点は，眉の位置の多くを顔の形から推定しているため（下記の試算），画像から眉毛を探す方法と組み合わせる．

1. Face Landmarkerで顔と目の位置をとり，頭の傾きを除いた座標にする．
2. 眉の中心線を2つの方法で求める．
   - Face Landmarkerの眉の点（上側と下側の点の中点）．
   - 画像から眉毛を探す方法．目の点だけで目の上の範囲を切り出し，周りの肌より暗い所を左右になめらかにつないだ線を求める．線の上で暗さがはっきりした区間を眉毛とし，上下のふちの中点を中心線にする．太すぎる所（横の髪），範囲の上の端に付いた所（前髪），目のすぐ上（まぶたのしわ）は除く．
3. 中心線から，眉頭（最も内側），眉山（黒目の外側と目尻の中間の位置．チームで調べた眉山の目安），眉尻（最も外側）の高さをとる．
4. 方法ごとの偏り（Face Landmarker：眉山 +0.018，眉尻 −0.137，画像から探す方法：眉山 +0.004，眉尻 +0.033）を引き，2つの平均で分類する．画像から眉毛が見つからない場合は，Face Landmarkerだけで分類する．
5. 撮影時は，無表情，正面，前髪を上げるように案内する．眉をひそめると眉の形が変わる．

**試算の結果（2026年11月7日）:** [SCUT-FBP5500](https://github.com/HCIILAB/SCUT-FBP5500-Database-Release)（非商用の研究のみ）のアジア人女性2000人の正面写真（350×350）で，人が付けた眉の点とFace Landmarkerの眉の点を比べた．写真と解析はローカルのPCだけで扱い，リポジトリには入れていない．

| 項目                                                     | 結果                                                 |
| -------------------------------------------------------- | ---------------------------------------------------- |
| 位置のずれ（中央値 / 90%）                               | 眉頭 0.15 / 0.24，眉山 0.16 / 0.27，眉尻 0.20 / 0.29 |
| 眉の高さの相関（人の点とFace Landmarker）                | 眉山 0.60，眉尻 0.66                                 |
| 眉尻の高さの偏り（Face Landmarker − 人の点）             | −0.14（Face Landmarkerがいつも低い）                 |
| 眉を消した写真との相関（人の点とFace Landmarker）        | 眉山 0.33，眉尻 0.44                                 |
| 人の点での眉の高さ（10% / 中央値 / 90%）                 | 眉山 0.14 / 0.19 / 0.26，眉尻 −0.02 / 0.08 / 0.17    |
| 顔の縦の長さの相関（額の上部の点10と，人が付けた生え際） | 0.72                                                 |

単位は目の横幅．Face Landmarkerは眉毛を一部見ているが，眉の位置の多くを顔の形から推定している．位置のずれが，人ごとの眉の高さの違いと同じくらい大きいため，眉の点だけでは5種に分けられない．また，仮の境目（±0.05，0.15）は実際の分布と合わない．

そこで，次の方法を試した．眉の形の評価は，境目と偏りを前半の1000人で決め，後半の1000人で確かめた．

| 試した方法                                                    | 結果                                                       |
| ------------------------------------------------------------- | ---------------------------------------------------------- |
| 眉山の境目の組み合わせを変える                                | 平行眉・微アーチ眉の範囲が狭くなるだけで，正解率は下がった |
| 眉山での角度（眉頭−眉山−眉尻）で測る                          | 人の点との相関0.29．高さ（0.60）より低い                   |

| Face Landmarkerと画像から探す方法の平均                       | 高さの相関は眉山0.69，眉尻0.75．単独の方法より高い         |

**決定:** 上記の方法で今の眉の形を5種に分類し，⑭の「今の眉」に出す．一致率は約5割で，微アーチ眉は当たりにくいことを受け入れる．写真はSCUT-FBP5500（350×350）が中心のため，端末のカメラの画質で精度を確かめることと，偏りの値を見直すことは，写真から診断を実装するときに行う．

## 5. 非機能要件

- **端末（確定）:** iOS・Androidのスマートフォン。iOSのUXを優先し、Androidでも全機能を動かす（スターター規約）。インカメラを使う。顔追跡のネイティブモジュールはExpo Goで動かないため、開発ビルド（EAS Build）で確認する。
- **ARの速さ（案）:** 顔の動きに重ね表示が遅れて見えないこと。目安は30fps以上、遅延100ms以下。PoCで実測する。
- **プライバシー（確定）:** ライブ顔追跡・AR表示・写真診断の映像、画像、特徴点は端末内に留める。録画・選択した動画は⑫-3で解析への明示同意を得た場合に送信し、APIで永続保存しない。プロフィール写真や公開用サムネイルは利用者が保存・投稿を選んだ時点で送信する。
- **明るさ:** 色を正しく見せるため、明るさを測り、暗いときは知らせる。
- **権利:** SNSから取り込んだレシピには投稿者名と元の投稿へのリンクを必ず表示する。
- **表示:** 色・文字はFoundationsに従う（下の「デザイン基盤」）。最小の文字は10px。実装planのライト配色を使う。
- **操作:** スターター規約どおり、独自UIの押せる範囲は48pt/dp以上にする。実装planの40pxのアイコンボタンは、見た目を保ったまま押せる範囲を広げる。
- **安全性:** 秘密情報をリポジトリに置かない。外部入力はZodで検証し、保護するAPIはBetter Authのセッションで認可する（スターター規約）。

## 11. AR表示の方式

ARの顔追跡には[MediaPipe Face Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)を必ず使う（確定）。塗る範囲は、顔の特徴点で作るメッシュにUVテクスチャを貼って重ねる（AR表現の比較のD案、確定）。

### 確認した事実（2026年11月7日）

- Face Landmarkerは1つの顔につき478点の3次元の特徴点を返す。x・yは画像の幅・高さで正規化した0〜1の値、zは頭の中心を基準にxと同じ尺度の奥行き。任意で52個のblendshapeと、標準の顔から検出した顔への4×4の変換行列を返す。
- 実行モードは `IMAGE` / `VIDEO` / `LIVE_STREAM`。`LIVE_STREAM` は非同期で結果を返し、処理が詰まると入力フレームを捨てて遅れを溜めない（iOS・Android）。
- モデルは `face_landmarker.task`（顔検出BlazeFace short-range 192×192、特徴点モデル256×256、blendshapeモデル）。既定は `num_faces=1`（1のとき時間方向の平滑化が効く）、各信頼度0.5。
- iOSはSwift Package Managerの `MediaPipeTasksVision`、Androidは `com.google.mediapipe:tasks-vision`。
- 標準の顔メッシュ [`canonical_face_model.obj`](https://github.com/google-ai-edge/mediapipe/blob/a908d668c730/mediapipe/modules/face_geometry/data/canonical_face_model.obj)（Apache-2.0）は頂点468・UV座標468・三角形898。三角形の各角は頂点番号とUV番号を別々に持つ（例：`f 174/43 156/119 134/220`）。頂点 i のUVが `vt[i]` とは限らないため、UVは必ず三角形の定義から引く。
- 特徴点478点のうち先頭468点が標準メッシュの頂点に対応し、残り10点が虹彩（468〜472が本人の右目、473〜477が左目。各5点の先頭が中心）。#26でエミュレーターの1フレームの特徴点を標準メッシュの頂点へ弱透視の射影で当てはめて確かめた。番号どおりの対応は平均4.0px（顔の幅149px）、1つずらすと平均36.7px。468・473は、それぞれ目の4点の中心から目の幅の0.19倍・0.23倍の位置にあり、残り4点の平均と0.2px以内で一致する。

### 処理の流れ（案）

1. インカメラの映像を端末内でFace Landmarkerの `LIVE_STREAM` へ渡し、特徴点を受け取る。映像はサーバーへ送らない。
2. 正規化座標を画面座標へ変換する。カメラ映像の拡大・切り抜きと、インカメラの左右反転を合わせる。左右反転した画像ではblendshapeの左右も逆になる。
3. 標準メッシュの三角形を使い、頂点の位置を画面上の特徴点、テクスチャ座標をUVにして描く。
4. 手順ごとのテクスチャは、標準メッシュのUV空間に描いた透過画像（PNG）にする。仕上がりの色を乗算で合成する。完成（⑩）では重ねない．塗る位置の案内であり，完成した顔に重ねると不自然に見えるため（#190）．
5. ピン・ラベル・矢印・補助線は、特徴点の番号かUV座標で位置を持ち、三角形の中の位置から画面座標へ写す。文字はアプリのUIとして重ねる。
6. 前髪の上に色が乗る問題は、髪の領域の切り出しで隠すまで、透明度で抑える。

### 手順のデータ（案）

手順ごとに、テクスチャ（画像の参照、合成方法、不透明度）と、注釈の一覧（種類、位置の基準、文言）を持つ。位置の基準は「特徴点の番号」か「UV座標」のどちらか。

### 暫定採用した構成

前面カメラとFace Landmarkerをアプリ内のExpo Moduleにまとめ、特徴点をJSへ渡してReact Native Skiaの頂点描画でUVテクスチャを重ねる。AndroidのCameraXとiOSのAVFoundationを使う。既存のExpo Moduleで端末上の追跡と3部位の表示を確認でき、追加のフレーム処理基盤やGL描画を要しないため、⑦⑩へ引き継ぐ暫定方式とする。ネイティブモジュールを含むためExpo Goでは動かず、新しい開発ビルドが必要。Android仮想端末の左右約30度の見た目は利用者の目視で確認した。iOSの実行、スマートフォン実機の性能、角度不明の横向きフレームで再現した奥側の折り返しへの対策は未検証であり、製品の表示品質を確定した判断ではない。

## 12. 検証の状況

2026年11月7日時点で確かめたのは、スターターの取り込み後の静的な検査（整形、lint、型、Bun・Jestのテスト、PostgreSQLでの認証テスト、expo-doctor、iOS・Androidのbundle生成、OpenTofuのvalidate）と、P1・P2のAndroid仮想端末での動作。PCカメラ映像上の正面は3部位の表示を確認し、左右約30度の見た目は利用者の目視申告である。角度の計測や画像による追加解析はしていない。実機での動作、iOSの開発ビルド、Google Cloudへのデプロイ、顔型差異は確かめていない。今回の依頼では5人での比較は行わない。

P1（#25）は、Androidのエミュレーター（Android 17、x86_64、6コア・4GB、`-gpu host -qemu -cpu host`）とPCのウェブカメラ（eMeet C960）で確かめた。478点が取れ、拡大・切り抜き・左右反転を合わせた画面座標で顔に重なる。顔を外すと案内が出て、戻すと追跡に戻る。カメラ権限を拒否したときの案内と設定ボタンも確認した。参考値はCPUの推論で11fps、遅延（フレームを受け取ってから結果が出るまで）は平均41ms・最大78ms。別の観測では11fps、平均67ms・最大174msだった。エミュレーターはカメラの映像とGPUの命令を変換して渡すため、GPUの推論は通常の方式では毎フレーム失敗し、ANGLE方式（`-feature GuestAngle`）では1回約400msかかった。この値は中位の端末の性能を表さないので、30fps以上・遅延100ms以下の実機目安は判定していない。左右約30度の追跡は利用者の目視では問題なかったが、角度は計測していない。真横を向くと外れることがある。iOSは、試したApple IDがApple Developer Programに入っておらず、開発ビルドを作れていない。
